❯ if we wanna keep <dialog>, then what would you recommend?

⏺ Instructions understood.

  Without JavaScript, <dialog> can't do a clean swap. No single button can close
  one dialog and open another. You'd have to work with the fact that modals
  stack. Here's how that behaves:

  - show-modal puts the new dialog on top. The current one stays open
    underneath. If each dialog covers the whole screen, readers won't see the
    one below.
  - close closes only the top dialog, which shows whatever is underneath.
  - Gotcha: show-modal on a dialog that's already open does nothing. It won't
    bring it to the front. So a "< Previous" button that runs show-modal on an
    earlier chapter that's still open underneath will look broken.

  One approach that fits this behaviour:

  <!-- inside chapter A -->
  <button command="show-modal" commandfor="chapter-b">Next</button>

  <!-- inside chapter B -->
  <button command="close" commandfor="chapter-b">Previous</button>

  "Next" stacks a new chapter on top, and "Previous" closes the current one to
  reveal the chapter below.

  Try this with your own chapters, and think about these cases:

  - What happens if someone opens Chapter 03 straight from the landing page and
    then clicks "Previous"?
  - Your Chapter 01 has a "< Chapter 06" button. What would a wrap-around do in
    a stack?

  If those cases break your design, that tells you <dialog> is the wrong tool
  for this navigation. The :target approach I mentioned earlier handles it
  without stacking.

  Reference: MDN: showModal() (https://developer.mozilla.org/en-US/docs/Web/API/
  HTMLDialogElement/showModal), which describes the "already open" behaviour.

❯ If we wanted to create a grid box borders like the reference, can we achieve
  it by adding border-block and border-inline to the nav ol and li? If not, how
  do we achieve it?

  Ran 1 shell command (ctrl+o to expand)

⏺ Instructions understood.

  I can't see your reference image, so please describe it or paste a screenshot.
  I'll assume it's a table-like grid where every cell is boxed and neighbouring
  cells share a single line.

  Will border-block and border-inline on ol and li work? Partly. You'll run into
  two problems:

  1. Double lines. Each item draws its own four sides. Where two lis meet, or an
     li meets the ol edge, you'll see two borders side by side, so those lines
     look twice as thick.
  2. Gaps. Your nav ol has gap: var(--spacing-sm). That puts space between the
     borders, so you'll get separate boxes instead of shared lines.

  Also, your nav ol is currently a single flex column, with lis at 60% width
  zig-zagging left and right. That's a different layout from a grid, so you'd
  change that first.

  Two common ways to get shared grid lines:

  A. Use the gap as the line. Give the container the line colour, make the gap
  the width of a border, and give each cell the background colour. The gap then
  shows through as the lines:

  .grid {
          display: grid;
          gap: 1px;               /* line thickness */
          background-color: black; /* line colour */
          border: 1px solid black; /* outer edge */
  }
  .grid > * {
          background-color: white;
  }

  B. Draw only some sides. Each cell draws just its end sides
  (border-inline-end, border-block-end). The container draws the start sides
  (border-inline-start, border-block-start). That way every line is drawn
  exactly once.

  A is usually simpler. B gives you more control, for example if only some lines
  should show.

  Your project is mobile-first. How many columns should the grid have on a phone
  compared with a wider screen?

  Reference:
  - Course site: Grid
    (https://typography-interaction-2627.github.io/topic/grid/)
  - MDN: gap (https://developer.mozilla.org/en-US/docs/Web/CSS/gap)
  - MDN: logical border properties
    (https://developer.mozilla.org/en-US/docs/Web/CSS/border-block)

❯ So is it possible to achieve the table-like grid w/o having content in every
  cell?

⏺ Instructions understood.

  Not directly. CSS grid doesn't draw cells, only tracks, and a track with
  nothing placed in it has no box to put a border or background on. Here's how
  that plays out with each approach:

  - A (gap as line): an empty area shows the container's background. With the
    example above, an empty cell would show as a solid black block, not an
    outlined box.
  - B (borders per side): borders only appear on items, so an empty area has no
    lines around it at all.

  Ways around it:

  1. Add empty elements. Put an empty element in each blank cell so it has a box
     to style. Inside an <ol> the only allowed children are <li>s, and empty
     <li>s would be read out as list items. That makes this a poor fit for your
     nav. It's fine in a grid that isn't a list.
  2. Draw the lines on the container. Use a background-image with
     repeating-linear-gradient to paint lines at regular intervals behind the
     items. This only works when your rows and columns have fixed, equal sizes,
     because the gradient doesn't know where the tracks actually are.
  3. Separate the lines from the content. Use a decorative grid layer (for
     example, a ::before on the container) that is itself a grid, with the nav
     items placed on top. This is more involved.

  Before choosing, look at your reference. Do the empty cells sit in
  predictable, evenly sized positions? If yes, option 2 is likely the simplest.

  Reference:
  - MDN: repeating-linear-gradient() (https://developer.mozilla.org/en-US/docs/W
    eb/CSS/gradient/repeating-linear-gradient)
  - MDN: <ol> permitted content (https://developer.mozilla.org/en-US/docs/Web/HT
    ML/Reference/Elements/ol#technical_summary)

❯ is there a way to do this with flex for the mobile version?

⏺ Instructions understood.

  Flex has the same limitation, and it's even more strict. Grid at least has
  tracks, but flex has no rows or columns at all, only items. Lines can only
  come from items or from the container.

  That doesn't have to be a problem on mobile, though. It depends on what the
  layout looks like:

  If it's one item per row, full width: flex works fine and there are no empty
  cells to worry about.

  - Give each li a border-block-end.
  - Give the ol border-block-start and border-inline.
  - Remove the gap, otherwise the lines won't touch.

  If it keeps your current zig-zag (each item takes 60% and sits on alternating
  sides, with an "empty" half that should still look boxed): the empty side has
  no element, so flex can't outline it. One way to fake it is to make each li
  full width, so the row itself is the box. Then:

  - Use justify-content (or align-items, depending on direction) inside the li
    to push the button to one side.
  - Draw any internal divider on the li itself. A border on the button, or a
    ::after pseudo-element, would both work.

  Now every row is a real element, so it can carry borders.

  Which of those matches your mobile reference? And does each row look split
  into two cells, or is it a single box?

  Reference:
  - Course site: Flexbox
    (https://typography-interaction-2627.github.io/topic/flexbox/)
  - MDN: ::after (https://developer.mozilla.org/en-US/docs/Web/CSS/::after)
